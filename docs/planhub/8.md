# Plan 8: Knowledge Base

Gemeinsame Grundlage: [0.md](0.md). Voraussetzung: [2.md](2.md) fertig.

## Ziel dieser Session

Kategorien, Artikel-Versionierung, Volltextsuche, Ticket-Verknüpfung,
Feedback-Widget.

## Aufgaben

- `knowledge_base_categories` (self-referencing `parent_id`) für den
  Kategorien-Baum.
- `knowledge_base_articles` mit Markdown-Body, Sichtbarkeit `internal`
  (nur Agenten/Admins) vs. `public` (auch im Self-Service-Portal sichtbar,
  siehe [10.md](10.md)) je Artikel.
- `knowledge_base_article_versions`: jede Veröffentlichung erzeugt neue
  Version, Diff-/Rollback-Ansicht im Admin-Bereich, aktueller Stand per
  `current_version_id`-Zeiger auf dem Artikel.
- Volltextsuche über MySQL-Fulltext-Index (kein Elasticsearch-Zwang);
  optionale Erweiterung auf `ticket_embeddings`-Vektorsuche für „ähnliche
  Artikel" (Wiederverwendung der KI-Embedding-Infrastruktur aus
  [6.md](6.md), DRY — falls [6.md](6.md) bereits umgesetzt, sonst später
  nachziehbar).
- Verknüpfung mit Tickets: Agent kann Artikel direkt aus dem Ticket heraus
  einfügen (Textbaustein-ähnlich) oder als „gelöst mit Artikel X"
  markieren.
- `knowledge_base_article_feedback` (hilfreich/nicht hilfreich, anonym
  zählbar), aggregiert im Management-Dashboard ([7.md](7.md), falls
  bereits umgesetzt).
- Permission-Slugs im `KnowledgeBase`-Modul: `kb.articles.view`,
  `kb.articles.manage`, `kb.categories.manage`.

## Verifikation

- Artikel-Veröffentlichung erzeugt neue Version, Rollback stellt
  vorherigen Stand wieder her.
- Volltextsuche findet Artikel nach Stichwort.
- Öffentliche Artikel sind für den späteren Portal-Zugriff markiert,
  interne nicht.
- Feedback-Widget speichert Bewertungen korrekt.
