# Plan 13: Globale MCP-API für KI-Telefonassistenten

Gemeinsame Grundlage: [0.md](0.md). Voraussetzung: [2.md](2.md) (Ticket-Kern)
fertig; baut auf der Team-API-Key-Infrastruktur aus [3.md](3.md) auf;
sinnvoll nach [8.md](8.md) (Knowledge-Base-Suche als Tool) und im
Zusammenspiel mit [11.md](11.md) (Audit-Log).

## Recherche-Grundlage (Web, 2026)

- **telli.de** (und vergleichbare KI-Telefonassistenten wie fonio, IONOS/
  STRATO-Smart-Telefonassistent) bieten „Custom Tools"/API-Anbindungen, mit
  denen der Voice-Agent während eines Telefonats live Daten abrufen oder
  Aktionen in einem externen System (CRM/Ticketsystem) auslösen kann; bei
  Bedarf erfolgt eine „Warm Transfer" an einen Menschen mit vollem
  Gesprächskontext. Es gibt keine öffentlich dokumentierte MCP-spezifische
  Integration von telli.de — die Anbindung erfolgt über deren generisches
  Custom-Tool/API-Interface, an das ein MCP-Endpunkt genauso angebunden
  werden kann wie ein klassischer REST-Endpunkt.
  ([telli auf OMR Reviews](https://omr.com/en/reviews/product/telli),
  [KI-Telefonassistent-Vergleich, Placetel](https://www.placetel.de/ratgeber/ki-telefonassistent))
- **MCP-Sicherheits-Best-Practices 2026**: Authentifizierung strikt von
  Autorisierung trennen (Verbindung ≠ automatischer Zugriff auf alle
  Tools), Tool-Allow-Listen statt „alles freischalten", Autorisierung bei
  **jedem** Tool-Aufruf neu prüfen (nicht nur beim Verbindungsaufbau),
  Session-IDs niemals als Autorisierungsnachweis behandeln.
  ([MCP Security Best Practices – getmaxim.ai](https://www.getmaxim.ai/articles/mcp-security-best-practices-enterprise-checklist-2026/),
  [Stack Overflow: Auth in MCP](https://stackoverflow.blog/2026/01/21/is-that-allowed-authentication-and-authorization-in-model-context-protocol/))
- **MCP-Tool-Design-Best-Practices**: ein Tool = eine klare Aufgabe
  (`create_ticket`, `search_tickets`, nicht ein Monolith-Tool), strikte
  JSON-Schema-Validierung der Eingaben, strukturierte Fehlerklassen
  (Client-/Server-/externe Fehler), **Idempotenz-Keys** bei erzeugenden
  Tools (verhindert doppelte Tickets bei Netzwerk-Retry durch den
  Voice-Agent), Cursor-basierte statt Offset-Paginierung bei Listen-Tools,
  Rate-Limiting per Token-Bucket je Client, Health-Check-Endpunkt.
  ([modelcontextprotocol.info Best Practices](https://modelcontextprotocol.info/docs/best-practices/))
- **OAuth vs. statischer Bearer-Token**: Die MCP-Spezifikation empfiehlt für
  interaktive, nutzergebundene Remote-Server OAuth 2.1 mit PKCE. Für
  **Server-zu-Server-Integrationen** (ein Telefonassistent-Anbieter, vom
  Team-Admin einmalig konfiguriert, kein menschlicher End-User-Login-Flow)
  ist ein scope-gebundener Bearer-Token gängige und ausreichende Praxis
  ([GitHub Blog: secure remote MCP servers](https://github.blog/ai-and-ml/generative-ai/how-to-build-secure-and-scalable-remote-mcp-servers/),
  [systemprompt.io: OAuth 2.1 + Least Privilege](https://systemprompt.io/guides/mcp-server-authentication-security)).

## Offene Frage → Antwort aus der Recherche

**OAuth-Server komplett neu bauen oder bestehende Team-API-Keys ([3.md](3.md))
wiederverwenden?** → Wiederverwenden. Ein voller OAuth-2.1-Autorisierungs-
Server wäre für den hier vorliegenden Fall (Team-Admin hinterlegt einmalig
einen Token in der telli.de-Konfiguration, kein interaktiver Endnutzer-
Consent-Flow) unnötige Komplexität (KISS, kein YAGNI). Die bestehende
`ApiClient`/Sanctum-Infrastruktur aus [3.md](3.md) wird um MCP-spezifische
Abilities erweitert, statt ein Parallelsystem zu bauen (DRY).

## Ziel dieser Session

Ein **globaler** MCP-Endpunkt (`/mcp`, ein Endpunkt für die gesamte
Installation, nicht pro Team/Mailbox), über den externe KI-Telefonassistenten
wie telli.de während eines laufenden Telefonats Tickets anlegen, Status
abfragen und die Wissensdatenbank durchsuchen können — team-gescoped über
denselben API-Key-Mechanismus wie die externe REST-API.

## Architektur

- Transport: **Streamable HTTP** (aktueller MCP-Standard für Remote-Server,
  ersetzt das ältere HTTP+SSE), JSON-RPC-2.0-Nachrichtenformat.
- Route `/mcp` (Guard `sanctum`), Auth über denselben Bearer-Token wie in
  [3.md](3.md) (`ApiClient`/`personal_access_tokens`), neue Ability
  `mcp.tools.use` zusätzlich zu `tickets.create` — ein Team-API-Key kann
  wahlweise für REST, MCP oder beides freigeschaltet werden (Abilities
  granular je Zweck, kein Alles-oder-Nichts).
- Team-Ableitung **ausschließlich** aus dem authentifizierten Token
  (`$request->user()->team_id`), niemals aus Tool-Parametern — gleiche
  Sicherheitsregel wie in [3.md](3.md).
- Autorisierung wird bei **jedem** Tool-Aufruf neu geprüft (nicht nur beim
  Verbindungsaufbau), gemäß Recherche-Best-Practice oben.
- Health-Check-Endpunkt `/mcp/health` (DB-Verbindung, Auth-Service).

## Tools (MVP)

Jedes Tool = eine klare Aufgabe, strikte JSON-Schema-Validierung über
dieselben `FormRequest`-Whitelist-Regeln wie in [3.md](3.md):

- `create_ticket` — legt Ticket an (`source = phone`, analog zu `api`/
  `whatsapp`), Pflichtfelder: Anrufer-Rufnummer, Zusammenfassung,
  optional Priorität (`Rule::in([...])`). **Idempotenz-Key** (vom
  Telefonassistenten mitgegeben, z. B. Call-ID) verhindert doppelte
  Tickets bei Retry.
- `search_tickets` — Suche nach offenen Tickets zur Anrufer-Rufnummer
  (Cursor-Paginierung), damit der Assistent bei Rückrufen den Kontext
  kennt.
- `get_ticket_status` — Status-Abfrage eines konkreten Tickets (nur
  innerhalb des eigenen Teams, Policy-Scope wie überall im Projekt).
- `add_call_note` — hängt Anruf-Zusammenfassung/Transkript als interne
  Notiz an ein bestehendes Ticket an (nutzt bestehende
  `ticket_messages`-Struktur aus [2.md](2.md), DRY).
- `search_knowledge_base` — durchsucht **nur die für diesen Key
  freigegebenen** `public`-Kategorien aus [8.md](8.md) (siehe „KB-Scoping"
  unten), damit der Assistent Standardfragen direkt am Telefon beantworten
  kann, aber nicht versehentlich Zugriff auf die komplette Wissensdatenbank
  bekommt.

Rate-Limiting je Token (Token-Bucket, Default analog zu [3.md](3.md): 60
Aufrufe/Minute), da Telefonassistenten in Lastspitzen viele parallele
Anrufe verarbeiten können.

## KB-Scoping: nur ein Teilbereich der Wissensdatenbank

Der Nutzer möchte, dass telli (und andere angebundene Telefonassistenten)
gezielt nur auf einen **abgegrenzten Bereich** der Knowledge Base zugreifen
kann — nicht automatisch auf alle `public`-Artikel. Ein Telefon-Voice-Agent
soll z. B. nur die „Telefon-FAQ"-Kategorie sehen, nicht interne
Troubleshooting-Tiefe, die zwar öffentlich, aber für ein Telefonat
ungeeignet ist.

- Neue Pivot-Tabelle `api_client_kb_categories` (`api_client_id` FK,
  `knowledge_base_category_id` FK) — pro MCP-fähigem Key wird eine
  Whitelist an KB-Kategorien (inkl. optional deren Unterkategorien)
  hinterlegt; leere Zuordnung = kein KB-Zugriff über `search_knowledge_base`
  (Fail-Closed statt Fail-Open, sicherer Default).
- `search_knowledge_base` filtert serverseitig zusätzlich zur Sichtbarkeit
  `public` (aus [8.md](8.md)) auf `category_id IN (...)` der für den
  jeweiligen `ApiClient` freigegebenen Kategorien — kein Tool-Parameter kann
  diese Einschränkung umgehen (gleiche Sicherheitsregel wie bei der
  Team-Ableitung aus dem Token).
- Team-Admin-UI (siehe unten) bekommt eine Mehrfachauswahl aus dem
  bestehenden Kategorien-Baum ([8.md](8.md)) beim Anlegen/Bearbeiten eines
  MCP-Keys.

## Team-Admin-UI

Erweiterung der bestehenden Seite `/agent/team/{team}/settings/api-keys`
aus [3.md](3.md) um:
- eine Ability-Auswahl beim Erstellen eines Keys („REST-API" / „MCP" /
  beides), keine neue separate Verwaltungsseite nötig (DRY, ein Ort für
  alle externen Zugänge eines Teams);
- bei aktivierter MCP-Ability zusätzlich die KB-Kategorien-Mehrfachauswahl
  aus dem obigen KB-Scoping-Abschnitt.

## Sicherheit/Compliance

- Jeder Tool-Aufruf wird im `audit_logs` protokolliert (Team, Tool-Name,
  Zeitpunkt, Erfolg/Fehler) — Erweiterung von [11.md](11.md).
- Strukturierte Fehlerklassen (Client-/Server-/externe Fehler) statt
  unspezifischer 500er, damit der Voice-Agent sinnvoll reagieren
  (nachfragen/eskalieren) kann.
- Kein Tool erlaubt Zugriff außerhalb des eigenen Teams — Policy-Scope wie
  bei allen bisherigen Kanälen.
- Anrufer-Rufnummern sind personenbezogene Daten (DSGVO) — Aufnahme in die
  GDPR-Commands aus [11.md](11.md).
- `search_knowledge_base` liefert ausschließlich Artikel aus den für den
  jeweiligen Key freigegebenen Kategorien — Fail-Closed bei leerer
  Zuordnung, keine implizite Vollzugriffs-Freigabe.

## Verifikation

- Team-Admin erstellt einen Key mit MCP-Ability, Verbindungsaufbau des
  MCP-Clients (`/mcp`) gelingt, ohne MCP-Ability wird der Zugriff verweigert.
- `create_ticket` mit identischem Idempotenz-Key (simulierter Retry) legt
  nur **ein** Ticket an.
- `search_tickets`/`get_ticket_status` liefern ausschließlich Tickets des
  eigenen Teams, fremdes Team liefert 403/leeres Ergebnis.
- Rate-Limit-Überschreitung wird korrekt abgewiesen (kein Duplikat-Zähler-
  Leck über mehrere Tools hinweg).
- Jeder Tool-Aufruf erzeugt einen nachvollziehbaren `audit_logs`-Eintrag.
- Ein MCP-Key mit Freigabe für Kategorie „Telefon-FAQ" liefert über
  `search_knowledge_base` nur Artikel dieser Kategorie; Artikel aus anderen
  `public`-Kategorien erscheinen nicht. Key ohne KB-Kategorie-Zuordnung
  liefert keine Ergebnisse (Fail-Closed).
- Feature-Tests decken Team-Scope, Idempotenz, Ability-Trennung REST/MCP
  und KB-Kategorie-Scoping ab.
