# Plan 17: Theme-System (wählbare, nachträglich erweiterbare Layouts)

Gemeinsame Grundlage: [0.md](0.md). Voraussetzung: [1.md](1.md) (Fundament,
Modul-Registry-Muster).

## Ziel dieser Session

Theme-Registry-Mechanismus, der beliebig viele Themes (Farbpaletten/Layout-
Varianten) verwaltet, mit dem bestehenden Musterlayout ("AuraDesk"-Vorlage,
`docs/planhub/professionelles_ticket_system_layout.html`) als vorregistriertem
Default-Theme, installationsweit durch den Admin umschaltbar, wirksam in
allen drei Frontend-Bereichen (`/agent`, `/admin`, `/portal`), und
nachträglich um weitere Themes erweiterbar ohne Deploy von Kern-Code.

## Aufgaben

- **`themes`-Tabelle + Migration**: `id`, `slug` (unique), `name`,
  `is_default` (bool), `active` (bool, vom Registry-Scan gesetzt) — analog
  zur `modules`-Tabelle aus [1.md](1.md).
- **`ThemeServiceProvider`**: scannt beim Boot `resources/themes/<slug>/
  theme.json`, validiert Pflichtfelder (Name, Vorschaubild, CSS-Variablen-
  Map), registriert/aktualisiert Zeilen in `themes`; fehlerhafte/
  unvollständige `theme.json` wird geloggt und übersprungen statt den Boot
  abzubrechen (gleiches Fehlerverhalten wie beim `ModuleServiceProvider`,
  [0.md](0.md) Abschnitt „Modularität").
- **`theme.json`-Schema**: `name`, `preview_image`, `css_variables`
  (Whitelist fester Variablennamen — Primär-/Akzentfarbe, Sidebar-
  Hintergrund, Text-/Rahmenfarben, abgeleitet aus den `calm`/`slatecalm`/
  `ocean`-Paletten der Vorlage —, keine beliebigen/nicht gelisteten Keys),
  optional `font_family`. Serverseitige Whitelist-Validierung beim Scan
  (Sicherheit: verhindert, dass ein später von Dritten abgelegtes Theme
  beliebiges CSS/HTML einschleust).
- **Default-Theme „Musterlayout"**: `resources/themes/musterlayout/
  theme.json` + zugehöriges CSS, 1:1 aus der Farbpalette der bestehenden
  Vorlage (`docs/planhub/professionelles_ticket_system_layout.html`)
  abgeleitet, `is_default = true`, wird bei frischer Installation
  automatisch aktives Theme.
- **CSS-Umschaltmechanismus ohne Theme-eigenen Build**: ein einziger
  Tailwind/Vite-Build (kein CDN, siehe [0.md](0.md) Tech-Stack); Themes
  wirken ausschließlich über CSS-Custom-Properties auf
  `<html data-theme="...">` — neues Theme = neue kleine CSS-Datei mit
  Variablen-Overrides, kein Rebuild der App nötig.
- **Gemeinsames Basis-Layout**: ein zentrales Blade-Layout (z. B.
  `resources/views/layouts/app.blade.php`), das von `/agent`, `/admin` und
  `/portal` eingebunden wird und serverseitig das aktive Theme aus den
  Settings liest und das `data-theme`-Attribut setzt — ein Mechanismus für
  alle drei Bereiche statt Insellösung.
- **Admin-UI `/admin/settings/theme`**: Kachel-/Listenübersicht aller
  registrierten Themes (Vorschaubild, Name), Auswahl des aktiven Theme
  (installationsweit, eine Einstellung für alle Nutzer, kein Per-User-
  Override). Speicherung des aktiven Theme in einer einfachen Key-Value-
  `settings`-Tabelle (prüfen, ob in [1.md](1.md)/[11.md](11.md) bereits ein
  Settings-Mechanismus vorgesehen ist, sonst hier neu anlegen).
- **Berechtigung & Audit**: Ändern des aktiven Themes nur mit bestehender
  Admin-Permission (`spatie/laravel-permission`, z. B.
  `system.settings.manage`); jeder Wechsel erzeugt einen `audit_logs`-
  Eintrag (altes/neues Theme-Slug, ausführender Admin) gemäß dem
  Audit-Log-Muster aus [0.md](0.md).

## Verifikation

- Ein neues Theme erscheint in der Admin-Übersicht, sobald ein Ordner
  `resources/themes/<name>/theme.json` (+ CSS) abgelegt wird — ohne
  Codeänderung am Kern.
- Frische Installation startet automatisch mit dem Musterlayout als aktivem
  Theme.
- Admin kann das aktive Theme umschalten; die Änderung wirkt sofort
  gleichzeitig in `/agent`, `/admin` und `/portal`.
- Ein Themewechsel erzeugt einen nachvollziehbaren `audit_logs`-Eintrag.
- Ein absichtlich unvollständiges `theme.json` (fehlendes Pflichtfeld) wird
  beim Boot geloggt und ignoriert, der Boot bricht nicht ab.
