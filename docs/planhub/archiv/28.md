# Plan 28: Update-Prüfung und Ein-Klick-Update aus GitHub-Releases

Gemeinsame Grundlage: [0.md](0.md).

## Ziel

Admins sehen im Adminbereich, wenn eine neuere Custovis-Version veröffentlicht wurde,
und können sie ohne Shell/FTP direkt aus dem GitHub-Release installieren.

## Umsetzung

- `UpdateChecker` fragt `api.github.com/repos/{repo}/releases/latest` ab (Repo über
  `custovis.update.repository` / `CUSTOVIS_UPDATE_REPOSITORY`), speichert das Ergebnis in
  `settings` (`update.latest_release`). Täglich per Scheduler/Web-Cron, manuell per Button.
- Banner `<x-update-notice />` im Admin-Layout, nur für `system.maintain`.
- `UpdateInstaller`: lädt nur das Release-Asset `custovis-vX.Y.Z.zip` von
  `github.com/{repo}/releases/download/`, prüft den SHA-256-`digest` von GitHub (ohne
  Digest keine Installation), lehnt Zip-Pfade mit `..`/absoluten Pfaden ab, kopiert ohne
  Löschen und ohne `.env*` (außer `.env.example`), `storage/`, `bootstrap/cache/`,
  `public/storage/`. Git-Checkouts werden verweigert.
- Nach dem Kopieren Redirect; die Migrationen laufen im Folge-Request mit neuem Code.
  Audit-Log `system.updated` (von/nach).
- Release-Workflow bricht ab, wenn `config/custovis.php` nicht zur Tag-Version passt.
- Tests: `tests/Feature/Admin/SystemUpdateTest.php`; Hilfe `resources/help/system.md`.

## Offen / Grenzen

- Dateien, die in einer neuen Version entfallen, bleiben liegen (wie bei `deploy.bat`).
- Kein Wartungsmodus während des Kopierens (wenige Sekunden).
