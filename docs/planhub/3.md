# Plan 3: Externe Ticket-Anlage-API mit teamverwalteten API-Keys

Gemeinsame Grundlage: [0.md](0.md). Voraussetzung: [2.md](2.md) fertig.

## Ziel dieser Session

Weiterer Eingangskanal neben Mailboxen (`source = api`), kein Ersatz für den
Maileingang. Verwaltung der API-Keys liegt dezentral beim **Team-Admin**,
nicht beim System-Admin — jeder Key ist genau einem Team zugeordnet.
Zusätzlich: GitHub-/GitLab-Issue-Import als weiterer Eingangskanal
(`source = git_issue`), siehe eigener Abschnitt unten.

## Architekturentscheidung

Eigenes, schlankes Modell `ApiClient` (`HasApiTokens`-Trait), 1:1 an ein Team
gebunden — kein Missbrauch echter Agenten-Accounts als Service-Accounts.
Nutzt die in [1.md](1.md) angelegte Sanctum-Infrastruktur (Guard `sanctum`)
mit, statt ein eigenes Key-System zu bauen (DRY).

## Aufgaben

- Migration/Modell `api_clients` (`id`, `team_id` FK, `name`, `created_by`
  FK `users`, `revoked_at` nullable, Timestamps) — ein Team kann mehrere
  benannte Clients haben.
- Token-Speicherung über Sanctums `personal_access_tokens` (polymorph
  `tokenable`), Abilities im MVP auf `tickets.create` beschränkt.
- Endpunkt `POST /api/v1/tickets` (Guard `sanctum`, Ability
  `tickets.create`), eigene `FormRequest` (`StoreExternalTicketRequest`) mit
  Whitelist-Validierung. Team wird **ausschließlich** aus dem
  authentifizierten `ApiClient` (`$request->user()->team_id`) abgeleitet,
  niemals aus dem Request-Body.
- Rate-Limiting je Token (Default 60 Anfragen/Minute) über Laravel
  `RateLimiter`.
- Ticket-Erstellung nutzt die bestehende Pipeline aus [2.md](2.md)
  (`tickets`/`ticket_messages`), nur `source = api` statt `source =
  mailbox`.
- Team-Admin-UI: `/agent/team/{team}/settings/api-keys`, Permission
  `team.api_keys.manage`, Policy-Scope auf das eigene Team. Key anlegen
  (Klartext-Anzeige einmalig), widerrufen, Liste mit letzter Nutzung
  (`last_used_at` aus Sanctum-Token).
- System-Admin-Ansicht: alle Team-Keys nur lesend (Compliance-Audit).
- Audit-Log-Eintrag bei Key-Erstellung/-Widerruf.

## Verifikation

- Team-Admin kann Key nur für eigenes Team erstellen/widerrufen,
  System-Admin sieht alle Keys nur lesend.
- Gültiger Key legt per `POST /api/v1/tickets` ein Ticket im korrekten Team
  an; widerrufener Key liefert 401; abweichendes Team im Body wird ignoriert
  (Team kommt aus dem Token).
- Rate-Limit-Überschreitung liefert 429.
- Feature-Tests decken Key-Scope, Team-Ableitung aus Token und Rate-Limiting ab.

## Zusatz: GitHub-/GitLab-Issue-Import

Neuer Eingangskanal `source = git_issue`, analog zur Mailbox aus [2.md](2.md):
Issues aus einem GitHub- oder GitLab-Repository werden automatisch als
Tickets angelegt bzw. synchronisiert, teamverwaltet wie die API-Keys oben.

### Aufgaben

- Migration/Modell `git_issue_connections` (`id`, `team_id` FK, `provider`
  enum `github`/`gitlab`, `repository` (z. B. `owner/repo` bzw.
  Projekt-Pfad), `access_token` verschlüsselt (Personal Access Token bzw.
  GitLab-Projekt-/Group-Token, analog zur verschlüsselten
  Mailbox-Zugangsdaten-Ablage aus [0.md](0.md)), `webhook_secret`
  verschlüsselt, `sync_mode` enum `webhook`/`poll`, `last_synced_at`
  nullable, `created_by` FK `users`, `revoked_at` nullable, Timestamps).
- Migration/Feld `tickets.external_ref` (nullable, z. B.
  `github:owner/repo#123`) zur Deduplizierung — verhindert doppelte Tickets
  bei wiederholtem Sync/Webhook-Replay.
- Zwei Sync-Wege, pro Connection wählbar:
  - **Webhook** (bevorzugt, echtzeitnah): Endpunkte
    `POST /api/v1/git-issues/github/{connection}` und
    `POST /api/v1/git-issues/gitlab/{connection}`, Signaturprüfung über
    `webhook_secret` (GitHub `X-Hub-Signature-256`, GitLab
    `X-Gitlab-Token`), kein Sanctum-Guard (Herkunft wird über die Signatur
    verifiziert, nicht über einen Bearer-Token).
  - **Polling-Fallback** (für Ziele ohne öffentlich erreichbaren Webhook-
    Endpunkt, z. B. rein FTP-gehostete Instanzen hinter NAT): Queue-Job
    `SyncGitIssuesJob` pro Connection, eigene Queue `git-sync`, Intervall
    konfigurierbar (Default 5 Minuten), nutzt `last_synced_at` für
    inkrementellen Abruf (GitHub `since`-Parameter, GitLab
    `updated_after`).
  - Beide Wege münden in denselben internen Service (`GitIssueImportService`),
    der Issue → Ticket/`TicketMessage` mapt (DRY, keine doppelte
    Mapping-Logik).
- Mapping: Issue-Titel → `tickets.subject`, Issue-Body → erste
  `ticket_message`, Issue-Autor → `ticket_messages.external_author_name`
  (kein Customer-Datensatz erzwungen), Issue-Kommentare → weitere
  `ticket_messages` (öffentlich), Issue-Status (`open`/`closed` bzw.
  GitLab `opened`/`closed`) → Ticket-Status-Mapping, Issue-Labels optional
  als Ticket-Tags.
- Antworten aus Custovis (öffentliche Antwort im Ticket) werden **nicht**
  automatisch zurück ins Issue gespiegelt (Scope-Begrenzung MVP — vermeidet
  Zyklen/Doppel-Postings); nur der Import-Weg wird umgesetzt.
- Team-Admin-UI: `/agent/team/{team}/settings/git-issues`, Permission
  `team.git_issues.manage` (analog zu `team.api_keys.manage`), Connection
  anlegen (Access-Token/Secret-Eingabe, nur einmalig im Klartext
  angezeigt bzw. gar nicht wieder angezeigt), Sync-Modus wählen, manuellen
  Sync-Anstoß, Verbindung widerrufen.
- Audit-Log-Eintrag bei Connection-Erstellung/-Widerruf, analog zu
  API-Keys.

### Verifikation

- Team-Admin kann Connection nur für eigenes Team anlegen/widerrufen.
- Ein neues GitHub-/GitLab-Issue erzeugt per Webhook oder Poll genau ein
  Ticket im korrekten Team; erneuter Webhook-Aufruf/Poll für dasselbe Issue
  erzeugt **kein** Duplikat (`external_ref`-Prüfung).
- Ungültige/fehlende Webhook-Signatur wird abgelehnt (401/403).
- Feature-Tests decken Mapping, Dedup über `external_ref` und
  Signaturprüfung ab.
