# Custovis - Service Suite – Architektur & Kontext (gemeinsame Grundlage)

Diese Datei bündelt die projektweiten Entscheidungen, auf die sich alle
Einzelpläne (`1.md` ff.) beziehen. Vor jeder Session zu einem Einzelplan
zuerst diese Datei lesen, dann den jeweiligen Schritt.

## Context

Neues, eigenständiges Open-Source-Projekt unter `D:\xampp1\htdocs\openticket`
(aktuell leer, kein Git-Repo): ein ITIL-konformes ITSM-/Ticketsystem, das die
Kernfunktionen etablierter Tools wie **FreeScout** (Shared-Mailbox-Ticketing),
**Zammad** (Self-Service, KI-Add-on), **iTop/GLPI** (Incident/Problem/Change/
Request-Management, CMDB) kombiniert – aber **ohne** deren Bezahlmodule/
Paywalls. Auslöser: ein Tool, das professionelles ITSM UND klassischen
Kundenservice per Shared Mailbox abdeckt, KI-Funktionen über selbst
konfigurierte API-Keys nutzt (keine Nachkauf-Kosten beim Hersteller), und
uneingeschränkt (Agenten/Tickets/Mailboxen) sowie DSGVO-/ISO-27001-konform
ist. Von Anfang an git-veröffentlichungsfähig (README, CHANGELOG, Lizenz,
Installer).

Recherche zu bestehenden Systemen (FreeScout, Zammad, iTop, GLPI, UVdesk,
Chatwoot, osTicket) zeigt: Kernfunktionen sind bei den meisten Open-Source-
Tools kostenlos, Zusatzmodule (Kanäle, KI, Customer Portal, White-Labeling)
sind meist kostenpflichtig. Custovis - Service Suite bietet bewusst alle diese Funktionen von
Anfang an frei und modular an.

**Projektname:** **„Custovis - Service Suite"** (von lat. *custos* – Wächter/Hüter),
GitHub-Name und `.de`-Domain frei, `.com` derzeit belegt (kein aktives
Produkt erkennbar). Vor endgültiger Markenanmeldung noch DPMA/EUIPO-Register
manuell prüfen.

**Grundsatzentscheidungen des Nutzers:**
- Lizenz: **AGPLv3** (schließt SaaS-Lücke, schützt Open-Source-Charakter dauerhaft)
- Frontend: **komplett eigenes Frontend** (Livewire/Blade/Alpine), **kein Filament** – sowohl Admin- als auch Agenten-Bereich selbst gebaut, für volle UX-Kontrolle
- Vorgehen: Grundgerüst (DB-Schema, Modul-Platzhalter, Routen für alle Phasen) zuerst je Bereich anlegen, Feature-Logik danach schrittweise füllen – daher die Aufteilung in Einzelpläne pro Session
- Zusätzlich gewünscht: **ein übergreifendes Management-Dashboard** sowie **ein Dashboard je Team**

## Tech-Stack & Kernentscheidungen

- **Laravel 12**, PHP 8.2+ (lokal PHP 8.2.12 / Composer 2.6.6 vorhanden), MySQL/MariaDB
- **Auth**: Laravel Fortify (Backend-Logik, kein aufgezwungenes UI) + Laravel Sanctum (API-Token). Getrennte Guards: `web` (Agenten/Admins, Tabelle `users`), `customer` (Self-Service-Portal, Tabelle `customers`), `sanctum` (API) – strukturelle Trennung verhindert versehentliche Rechte-Vermischung.
- **Rechte**: `spatie/laravel-permission` für globale/modulweite Permissions (z. B. `tickets.view.all`, `changes.approve`). **Eigenes** `teams`/`team_user`-Modell (statt Spatie-Teams-Feature) für Team-/Abteilungszugehörigkeit mit Rolle-im-Team, da Spatie-Teams für Multi-Tenancy gedacht ist und hier ein User in mehreren Teams mit unterschiedlichen Rollen sein kann.
- **Frontend komplett eigen**: Livewire/Volt + Blade + Alpine.js für alle drei Bereiche:
  - `/admin` – Administration (Nutzer/Team/Mailbox/Modul-Verwaltung, SLA-Regeln, Reports, Management-Dashboard)
  - `/agent` – Ticket-Arbeitsoberfläche (Threads, interne Notizen, Collision Detection, Team-Dashboard)
  - `/portal` – Kunden-Self-Service-Portal
  - Kein Filament-Dependency, volle Kontrolle über UX inkl. Dashboards.
- **Echtzeit**: Laravel Reverb (kostenloses, offizielles WebSocket-Paket) für Collision Detection und Live-Dashboard-Updates statt Pusher.
- **Mailbox-Handling**: `webklex/laravel-imap` für IMAP-Polling, pro Mailbox eigener Queue-Job (`FetchMailboxJob`), SMTP/IMAP-Zugangsdaten verschlüsselt pro Mailbox-Datensatz in der DB (nicht nur global in `.env`), da unbegrenzt viele Mailboxen unterstützt werden.
- **Queues**: DB-Treiber als Standard (Cron-kompatibel, kein Redis-Zwang für einfaches Hosting), Redis+Horizon als optionales Produktionsprofil. Getrennte Queues: `mail-fetch`, `mail-send`, `ai-processing`, `whatsapp`, `notifications`, `default`.
- **Status-Machines**: `spatie/laravel-model-states` für Incident/Problem/Change/Request-Status statt Eigenbau (erprobte Transition-Validierung, Events als Hook für Audit-Log/SLA).
- **Routing**: self-hosted **OSRM/Nominatim** für Distanz-/Dauer-Berechnung und Kartendarstellung (Leaflet + OSM-Tiles) in der Techniker-Einsatzplanung ([14.md](14.md)) — EU-/DSGVO-konform, kein Google-Maps-Vendor-Lock.
- **Mobile Techniker-Oberfläche**: Progressive Web App (`/field`, [14.md](14.md)) auf Basis des bestehenden Livewire/Blade/Alpine-Stacks mit Service Worker + IndexedDB-Offline-Queue statt separater nativer App.

## Datenmodell-Grundgerüst (Referenz, wächst pro Session)

Gemeinsame Basistabelle `tickets` (type: incident/problem/change/service_request/support_ticket, source: mailbox/api/whatsapp/git_issue) mit typspezifischen 1:1-Erweiterungstabellen statt vier komplett getrennten Hauptmodellen – vermeidet Duplizierung von Konversation/SLA/Team-Zuweisung (DRY), hält ITIL-Felder aber sauber typisiert. `tickets.external_ref` (nullable) dient der Deduplizierung bei extern importierten Tickets (z. ## Modularität

```
app/Core/            # Ticket-Basis, Team, User, Permission-Grundgerüst
app/Modules/
  IncidentManagement/  ProblemManagement/  ChangeManagement/
  ServiceCatalog/  KnowledgeBase/  TeamChat/  AiAgent/  Cmdb/  Reporting/
  FieldService/
    Providers/<Name>ServiceProvider.php
    Models/ Http/ Livewire/ Policies/
    module.json  routes.php  config.php
```
Zentraler `ModuleServiceProvider` scannt `module.json`-Dateien beim Boot,
registriert nur Module mit `enabled=true` in der `modules`-Tabelle. Core hängt
nie von Modulen ab; Modul-Abhängigkeiten werden deklariert und bei Zyklen mit
Log-Warnung deaktiviert statt den Boot zu crashen. Jedes Modul deklariert seine
Permission-Slugs; Zuschaltung je User/Usergruppe über `module_user`/`module_role`
getrennt von den generellen Permissions (Modulzugriff ≠ Handlungsberechtigung
innerhalb des Moduls).

## Repo-Struktur (Ziel, wird in [1.md](1.md) angelegt, in [12.md](12.md) veröffentlicht)

```
custovis/
  app/ bootstrap/ config/
  database/migrations/ database/seeders/
  docs/ (architecture.md, modules.md, ai-integration.md, compliance/)
  installer/ (Web-Installer: /install-Route, aktiv nur ohne .env/APP_INSTALLED)
  public/ resources/views/
  routes/ (web.php, portal.php, agent.php, api.php, console.php)
  tests/ (Feature/, Unit/)
  .env.example  README.md  CHANGELOG.md  LICENSE (AGPLv3)  CONTRIBUTING.md  SECURITY.md
```
Da kein SSH auf Zielservern besteht (nur SFTP/FTP), zwei Installationswege:
1. Composer-basiert (`composer install && php artisan custovis:install`) für
   Server mit Shell-Zugriff.
2. **Web-Installer** unter `/install` für reine FTP/SFTP-Ziele: geführter
   Browser-Wizard (DB-Test, Migrationen, Admin-Anlage) über authentifizierte
   Web-Routen statt Shell; nach Abschluss hart deaktiviert
   (`storage/installed.lock`). Spätere Schema-Updates ebenso über eine
   admin-only Route (`/admin/system/migrate`, Permission `system.maintain`).
